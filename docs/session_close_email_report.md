# Session-Close Email Report — Backend Spec

## Purpose

When a cashier closes a cash session in the POS, the POS posts the full Z
report (sold products, payment-method totals, cash counted vs expected,
variance, notes) to a new backend endpoint. The backend forwards it as an
email to the store owner. The POS does not know the owner's email — that's
configured on the tenant record server-side.

This is **fire-and-forget from the cashier's perspective** — closing a
session never blocks on the email succeeding. The POS uses its existing
pending-operations queue + retry pipeline (the same one that handles offline
order updates) so a flaky LAN, a backend outage, or a logout/login mid-flight
all degrade gracefully without dropping the report.

---

## Endpoint

```
POST /api/pos/cash-sessions/{session_code}/email-report
```

| Header | Value | Notes |
|---|---|---|
| `Authorization` | `Bearer {access_token}` | Same token used by every other `/pos/*` endpoint. |
| `Content-Type` | `application/json` | |
| `X-POS-Name` | e.g. `Caisse 1` | Already set by the POS interceptor. Use in the email subject. |
| `X-Tenant-ID` | tenant UUID | Already set. Drives the owner-email lookup. |

`{session_code}` is the POS-generated session code (also present in the
payload). Path + body redundancy is intentional — the path makes the
endpoint REST-shaped, the body is what the email is built from.

### Field semantics

| Field | Notes |
|---|---|
| `client_request_id` | UUIDv4 generated by the POS when the request is queued. **This is the idempotency key.** |
| `session.code` | Globally unique per tenant. Format `S-YYYY-MM-DD-NNN`. Must match the path param. |
| `session.money_at_start` / `money_at_end` | What the POS computed. `money_at_end` = open + cash sales − refunds − cash payouts. |
| `session.counted_cash` | What the cashier physically counted. May be null if the count-cash feature wasn't run (legacy sessions only). |
| `session.variance` | `counted_cash − money_at_end`. Negative = short. |
| `totals.by_payment_method` | All four keys always present even if zero, to keep the email template simple. |
| `totals.discount_total` | Order-level + line-level discounts combined. |
| `products[]` | One row per `(product_id, category_id, station_id)` triple. A single product appearing under two stations (multi-station product, see [[per-station-printing]]) appears once per station. |
| `z_report.z_number` | Monotonic per cashier per day. POS-generated. The backend should treat as opaque. |
| `z_report.issued_at` | Wall-clock at which the POS finalized the Z, after `session.ended_at`. |

All currency amounts are in the tenant's currency (the POS does not convert).
The currency code is in `totals.currency`.

## Idempotency

The triple `(tenant_id, session.code, client_request_id)` is the dedup key.

- **First successful processing** → store the request, send the email, return
  `{"status": "sent", ...}`.
- **Same key seen again** → don't send a second email; return
  `{"status": "already_processed", ...}` with the original `sent_at`.
- **Same `session.code` but different `client_request_id`** → this is a
  legitimate replay (the POS dropped the original op and re-queued, e.g. the
  cashier closed-then-reopened-then-closed the same session — yes, supported
  via the existing session model). Treat as a NEW report and send a fresh
  email. Including the cashier and the timestamps in the email body makes
  these distinguishable.

The POS will keep retrying any non-2xx until it receives a 2xx, so the dedup
table needs to retain at least the last 30 days of `(session_code,
client_request_id)` keys.

---

## Auth model

Use the existing `/pos/*` auth model:

- `Authorization: Bearer <token>` issued at POS login.
- 401 → POS sync pipeline already handles token refresh + retry; no special
  handling needed here.

The endpoint is scoped by `X-Tenant-ID`. Cross-tenant access (a token from
tenant A trying to email-report a session from tenant B) must return 403.

---

## Owner / recipient resolution

Backend-side configuration. Recommended schema addition:

```sql
ALTER TABLE tenants
  ADD COLUMN report_recipients TEXT[];        -- e.g. ['owner@x.com', 'manager@x.com']
ALTER TABLE tenants
  ADD COLUMN report_locale     VARCHAR(8);    -- 'en' | 'fr' | 'ar' for the email template
```

If `report_recipients` is empty or NULL → log a warning and return 200 with
`{"status": "sent_to_no_recipients"}` so the POS marks the op completed
(retrying won't help — recipients are a config problem, not a transport
problem).

## Email content

Subject:

```
[POS Z Report] {tenant.business_name} · {pos_name} · {ended_at | localized date}
```

Body (HTML — render server-side using the tenant's `report_locale`):

1. **Session header**
   - Cashier name, POS name, business name
   - Open/close timestamps (formatted in the tenant's timezone)
2. **Cash count block** (highlight variance in red if non-zero)
   - Expected: `money_at_end`
   - Counted: `counted_cash`
   - Variance: `variance` (signed)
   - Notes: `count_notes` if present
3. **Payment-method totals** — table with one row per method
4. **Top sold products** — table sorted by `net_revenue` desc, all rows
   (don't paginate; the kitchen needs the full picture)
5. **By category** — small summary table
6. **By station** — small summary table
7. **Other totals** — orders, tickets, discounts, refunds, voided, unpaid

Plain-text fallback: same data, simpler layout. Both bodies sent on a single
multipart message.

Optional V2 — attach a PDF of the same report. Out of scope for V1.

## Responses

| Code | Body | POS behavior |
|---|---|---|
| 200 | `{"status": "sent", "email_recipients": ["..."], "sent_at": "..."}` | Mark queue op completed. Show green snackbar. |
| 200 | `{"status": "already_processed", "sent_at": "..."}` | Same as `sent`. Idempotency path. |
| 200 | `{"status": "sent_to_no_recipients"}` | Mark completed. Log warning client-side; don't retry. |
| 400 | `{"error": "...", "field": "..."}` | **Do not retry.** Log via `Logger.instance` and drop the op. Indicates a payload bug — file as a POS bug. |
| 401 | `{"error": "unauthorized"}` | Existing auth-refresh path; then retry. |
| 403 | `{"error": "tenant_mismatch"}` | Drop op; log. Indicates a deeply broken state (POS token doesn't match the session's tenant) — alert. |
| 404 | `{"error": "session_not_found"}` | Drop op; log. The session was never synced to the backend; the email-report can't help. |
| 422 | `{"error": "...", "field": "..."}` | Same as 400. |
| 5xx | (anything) | Keep queued; retry next sync cycle. |
| Network error | n/a | Keep queued; retry next sync cycle. |

POS-side: the queue's `retry_count` increments on every non-success; if it
exceeds 10 the op is marked `permanently_failed` and the cashier sees the
orange snackbar above on the next manual sync. No automatic data loss.

## What the backend stores

Recommended minimum:

```sql
CREATE TABLE session_email_reports (
  id                BIGSERIAL PRIMARY KEY,
  tenant_id         UUID NOT NULL,
  session_code      VARCHAR(64) NOT NULL,
  client_request_id UUID NOT NULL,
  payload           JSONB NOT NULL,          -- full request body as received
  recipients        TEXT[] NOT NULL,
  status            VARCHAR(32) NOT NULL,    -- 'sent' | 'sent_to_no_recipients' | 'failed'
  email_provider_id VARCHAR(128),            -- SES/Mailgun/etc message id
  sent_at           TIMESTAMPTZ,
  received_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, session_code, client_request_id)
);
```

The UNIQUE constraint is the idempotency enforcer at the DB level. On a
duplicate INSERT, return the existing row's `sent_at` in the
`already_processed` response.

Index on `(tenant_id, session_code)` to make backfill / debug queries fast.

Retention: 90 days of full payloads is plenty for "the owner says they never
got the email"-grade debugging. After 90 days, prune the payload column but
keep the dedup row (`payload = NULL`) so the idempotency invariant holds
forever.

## Operational concerns

- **Rate limiting:** sessions close maybe once or twice a day per cashier.
  No special rate limit needed beyond the existing `/pos/*` limits.
- **Email provider failure:** if the provider POST fails (SES/Mailgun down),
  do NOT return 5xx to the POS. The POS would retry the whole report. Instead,
  enqueue the email send in a backend retry queue and return 200 immediately
  — the row in `session_email_reports` records `status='queued'` until the
  retry succeeds. This avoids amplifying provider outages into POS retry
  storms.
- **Timezone:** render all timestamps in the tenant's configured timezone.
  ISO strings in the JSON are always UTC.
- **i18n:** owner emails can be in `en`/`fr`/`ar` per the tenant's
  `report_locale`. Templates ship server-side; POS doesn't pick the language.

---

## Out of scope

- Real-time push of per-order events (the POS already syncs orders via
  `/pos/orders`).
- PDF attachments / printable Z reports — V2.
- SMS notification — V2.
- Multi-recipient routing rules ("send cash variance > 100 to the regional
  manager") — V2.

## Test plan (backend)

1. POST a fresh report → 200 `sent`, owner receives email, row in
   `session_email_reports` has `status='sent'`.
2. POST the same payload again → 200 `already_processed`, no second email,
   no new row, returned `sent_at` matches the first.
3. POST with the same `session.code` but new `client_request_id` → 200
   `sent`, owner receives a SECOND email, new row.
4. POST with tenant A's token against tenant B's session → 403.
5. POST with `report_recipients = []` → 200 `sent_to_no_recipients`.
6. Simulate email-provider failure → 200 to POS, row `status='queued'`, the
   backend retry queue sends the email when the provider recovers.
7. POST with a malformed payload (missing `session.code`) → 400.
8. Hit the endpoint with no `Authorization` → 401.
